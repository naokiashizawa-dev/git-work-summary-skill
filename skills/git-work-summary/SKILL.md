# Gitの変更から作業報告を作る

コミット履歴と差分を根拠に、何を作ったか・何が直ったかを日本語の箇条書きにまとめる。文章は依存スキル `natural-japanese` で整える。

## 前提と範囲

- Gitリポジトリ、Git 2.37以降、Python 3.10以降、`natural-japanese` が必要。
- `natural-japanese` は実行環境のスキル一覧から探し、その `SKILL.md` を読む。個人の絶対パスや、このスキルからの相対位置を仮定しない。見つからなければ未導入であることを伝える。Gitの調査は進めてよいが、整文スキルを使ったとは報告しない。
- 調査は読み取り専用。コミット、ステージ、checkout、fetch、push、ファイル修正や外部サービスへの投稿は、この依頼からは行わない。

## 1. 対象を決める

「今日」は実行時の現在日とユーザーのタイムゾーンで決める。以前の会話の日付を引き継がない。タイムゾーン指定がなければ環境のローカル時刻を使い、UTCだと決めつけない。

既定は現在のリポジトリ全体と現在のHEADから辿れる履歴。ブランチや作者の指定があればそれに従う。「今日の作業」だけで全ブランチや特定作者に広げない。共有ブランチの履歴を、すべて依頼者本人の作業と言い換えない。

日付の基準は **コミット日時（committer date）**。作者日時とは区別する。指定日の0時以上、翌日の0時未満を対象にする。

## 2. 履歴と変更ファイルを集める

このスキルの所在を基準に補助スクリプトを実行する。下記のパスは実際のスキルの場所、日付・オフセットは依頼時の値に置き換える。

```text
python "<skill-dir>/scripts/collect_commits.py" --repo "<repo-dir>" --date YYYY-MM-DD --utc-offset +09:00
```

日付・オフセット省略時は実行環境の今日を使う。ユーザーのタイムゾーンが環境と違うときは明示する。夏時間のある地域はその日の正しいオフセットを確認する。環境のローカル時刻を使う場合は、夏時間による日付境界の変化にも対応する。

`--ref <branch>` で指定ブランチを参照できる。checkoutは不要。浅いクローンでは `shallow` がtrueになるので、履歴の範囲が限られる可能性を必要に応じて伝える。0件なら「対象日のコミットはありません」と伝え、前日の内容を今日の実績に混ぜない。

補助スクリプトが使えない場合は、同じ日時範囲で `git log --since-as-filter=<start> --until=<end>` を取得し、`%cI` または `%ct` で翌日0時のコミットを除外する。普通の `--since` は、日時が前後した履歴で探索を打ち切る場合がある。PythonだけがなくGitは使える場合も、調査を止める必要はない。

## 3. 差分で作業内容を確かめる

履歴の件名と変更ファイルを見て、関連するコミットをまとめる。実際の動作・画面・データ形式が分かる差分を読む。

```text
git -C "<repo-dir>" show --format=fuller --stat <hash>
git -C "<repo-dir>" show <hash> -- <relevant-path>
```

補助スクリプトの件名・ファイル一覧だけで完了にしない。ファイルパスはリポジトリルート基準。独立した読み取りはまとめて実行し、大きいPrefab・バイナリ・生成物は必要な箇所に絞る。バイナリは内容を確認できた範囲だけ書く。

テストの追加は「テストを追加」と書けるが、差分を見ただけで「テスト通過」「実機確認済み」とは書かない。マージや生成物更新を同じ機能の別作業として水増ししない。取り消し・再修正があるときは最終的な変更に合わせて書く。コミット数を書くなら、集計対象と一致させる。

## 4. 依頼されたときだけ、未コミット分から予定をまとめる

「作業中のタグ変更も明日やることに」のような依頼がある場合、補助スクリプトに `--include-working-tree` を付ける。staged・unstaged・untrackedを調べ、対象に関係する差分と設計・計画資料だけを読む。

未コミットの変更は完了実績に含めず、「明日やること」または指定された予定欄に置く。変更が存在するだけで、テスト済み・完成済みとは判断しない。設計資料の予定とコードで着手済みの範囲を照合し、「続きを進める」「移行・表示・動作確認を行う」など、残作業が伝わる形にする。既存計画を要約する範囲に留め、新しい仕様や無関係な変更を加えない。作業中の内容が不明なら、その点だけ確認する。

## 5. natural-japaneseで整えて返す

`natural-japanese` の既定のクイック工程を使う。箇条書きの並列性を保ち、一項目に一つの機能・修正目的を置く。関連する文言・DB・生成物の更新は、読みやすい範囲で同じ項目にまとめる。

- 「何を変えたか」「どう便利になったか・何が直ったか」を先に書く。
- 詳細なファイル名・ハッシュ・コードは、依頼や説明上の必要がある場合に添える。
- 件数や文字数を埋めるために項目を増やさない。件数と箇条書きの数は同じでなくてよい。

整文後は依存スキルのlintと通読を行う。lintがPEP 723の依存宣言を持つ版なら `uv run "<natural-japanese-dir>/scripts/lint.py" --json "<temp-file>"` を使う。単に `python` で実行すると形態素解析の依存不足で失敗する場合がある。uvや依存パッケージが利用できないときは、依存スキルの `references/manual-checklist.md` に従い、lint未実行であることを短く伝える。検査成功を捏造しない。自分で作った一時ファイルだけ片付ける。

出力例（依頼に応じて予定欄は省略）:

```markdown
**今日（M月D日）の作業：コミット済みN件**

- 編集画面の波形を改良し、音の立ち上がりを見分けやすくした。
- タブ切り替え時に前の一覧が残る不具合を修正。

**明日（M月D日）やること**

- 作業中のタグ変更を進め、保存・再読込・絞り込みを確認する。
```

最終確認では、各項目に根拠となる差分があるか、実績と予定が混ざっていないか、対象日・ブランチが一致しているかを確かめる。
